Synergy Application Guide

Features workflows and technical structure

Synergy helps early-stage founders find complementary startup partners and mentors, then turn those connections into completed collaborations through a shared workspace.

This guide explains the current application for users, project reviewers and maintainers. It covers what each area does, how people move from a match to a completed engagement, how the matching engine works, and how the app stores and protects shared work.

Synergy currently runs as a local-first React and Node.js prototype. Its default sign-in is simulated, while a separate local account mode supports real two-person collaboration. Shared agreements, milestone confirmations and private reviews are central to how the app works.

1 Purpose and users

Founders often need resources they do not have: product feedback, beta testers, distribution, technical support or experienced advice. Finding someone is only the first step. A useful connection also needs a clear agreement, owners, deadlines and a way to establish that the work was completed.

Synergy connects discovery with execution. Profiles describe what a person or startup offers and needs. Matches help users identify a useful counterpart. Accepted introductions create rooms where both participants agree on terms, communicate, organize tasks, provide evidence and confirm progress.

UserTypical purposeMain activities
Startup founderFind a startup partner or mentorDescribe offers and needs, browse matches, send introductions and complete exchanges or mentorships.
MentorHelp startups with a defined challengeDescribe expertise and availability, review startup needs, agree on goals and organize guidance and follow-up.
ModeratorMaintain the workspace and handle concernsReview reports, disputes and affiliation requests; manage vocabulary, templates and matching settings.

Accounts can support founder and mentor profiles. The active profile determines the relevant matches, rooms and profile information. Switching profiles is confirmed in Settings, and each role keeps its own draft profile.

2 Getting started and profiles

Default prototype sign in

With SYNERGY_DEMO_MODE=true, enter any non-empty email and password, select Founder or Mentor in the Prototype role dropdown, and sign in. These values simulate entry and do not need to be real credentials. Each entry creates a separate preview account with editable sample profiles.

The preview directory contains 24 fictional collaborators: 14 startups and 10 mentors. Preview accounts cannot discover or connect with one another. A pending outgoing introduction to a verified fictional fixture can expose Simulate acceptance, which creates a room for exploration. That action does not simulate the partner's later agreement, milestone confirmations or review.

Local account mode

Set SYNERGY_DEMO_MODE=false and restart the server to use local signup and password sign-in. For a complete reciprocal demonstration, create two local accounts in separate browser tabs, finish their profiles, and operate each side of the collaboration. Local passwords are salted and hashed with scrypt. This mode does not enable an external identity provider.

Sessions belong to a browser tab and survive a refresh. A server restart ends sessions. Signing out leaves the account and its saved work in storage; it does not reset the workspace.

Profile information

A founder profile includes an introduction, what the startup offers and needs, its industry, stage and team size. A mentor profile includes an introduction, offers and needs, expertise, availability and the kinds of startups the mentor wants to help. Additional context can include experience, goals, engagement preferences, audience size and standardized offer or need tags.

The completion indicator measures whether the role's core fields have content. It is a completeness measure, rather than a quality rating or identity verification. Clear, specific needs and offers give the matching engine more useful inputs.

Profile viewing and editing use separate layouts. Edits remain drafts in the current tab until Save profile succeeds. Typing, leaving a field or pressing Enter in a text field does not publish changes. Cancel restores the published profile. Successful sign-out clears this tab's drafts.

Profile photos accept JPEG, PNG or WebP up to 5 MB. Users can preview, replace or remove a photo before saving. The server validates the image, strips metadata and stores a bounded WebP version. Corrupt, animated and over-40-megapixel images are rejected.

4 How matching works

Matching estimates how well profiles complement one another. Startup exchanges consider both directions: what your startup needs from the other startup and what that startup needs from you. Mentorship compares the founder's needs with the mentor's offers and expertise.

The current engine is rule-based. It normalizes Unicode text, compares word coverage and maps a small set of related terms, such as testing and beta, to shared concepts. It does not call an AI model or infer a person's abilities beyond the supplied profile information.

FactorMeaningStartup exchangeMentorship
Need fitHow well needs are covered by the counterpart's offers50%35%
Expertise fitHow well mentor expertise covers founder needs0%25%
Industry fitOverlap in industry context or the mentor's startup interests20%15%
Stage or size fitStage compatibility and available team or audience size context15%10%
Goal fitShared goal wording and compatible engagement preferences15%15%

These are the default weights; moderators can manage versioned settings. The app multiplies each factor by its weight, adds the results and rounds to a percentage-style score. For startup need fit, the geometric mean of the two directional coverage values reduces the score when only one side benefits. Co-marketing-related size comparisons use audience size when supplied; other startup comparisons use team size.

Missing information earns no positive signal for the missing input. A low score can therefore reflect an incomplete profile as well as poor alignment. The score is a provisional estimate of profile fit, rather than a probability of success, a verification badge or a guarantee of a useful relationship.

Finding and saving people

Suggested surfaces eligible profiles with at least 30% fit. Browse all also includes weak and zero-fit profiles. Saved keeps bookmarked profiles available without sending an introduction. Existing active collaborations and account eligibility rules also affect what is shown.

Filters support text search, collaborator type, industry, engagement and minimum fit. Minimum fit accepts whole percentages from 0 to 100; an empty field or Reset removes that minimum. Applying filters narrows the current list without changing anyone's score or overriding visibility and blocking rules.

The fit explanation includes factor scores, missing inputs and directional coverage. Matching algorithm and weight versions are recorded, and rooms retain matching snapshots so outcomes can be compared with the configuration used when a collaboration began.

5 Introductions and rooms

A saved profile is a bookmark. An introduction is a request to collaborate. Users send an introduction from Matches, and the other participant accepts it to create a shared room. Founder pairs can choose a Beta Testing Exchange or Co-Marketing Swap; founder and mentor connections use Mentorship.

Introductions remain separate from active rooms so people can review a request before committing to a workspace. The preview-only simulated acceptance action is restricted on the server to eligible fictional profiles. Repeating it reuses the same room, and it cannot accept real participants' requests on their behalf.

StageMeaning
MatchedThe introduction has been accepted and the shared room exists.
Terms agreedThe agreement confirmation step. The interface identifies whose confirmation is still needed.
In progressBoth collaborators have agreed to terms and are carrying out the work.
Launched or CompletedThe collaboration has passed the completion requirements. Mentorship uses Completed; exchanges use Launched.
ReviewedBoth private reviews have been submitted and released.
ClosedThe unfinished collaboration has ended. Shared records remain accessible to participants.

A room has Terms, Milestones, Task board and Chat tabs. Mentorship also has Schedule. Room progress is based on milestones confirmed by both people.

6 Managing shared work

Terms and expectations

Terms record the shared goal, scope and deliverables, timeline, commitment and compensation or exchange expectations. Both people should understand what will be delivered and how success will be assessed before beginning.

A local terms draft must be saved to share it. Both participants confirm the agreement. If another participant changes the saved terms while a user is editing, the interface preserves the draft and asks the user to review the newer version. This protects shared work from stale edits.

Engagement templates

Templates supply the starting milestone checklist and evidence requirements. The current templates are:

  • Beta Testing Exchange: Scope defined, Testers assigned, Testing round, Feedback submitted and Issues reviewed. Testing round and Feedback submitted require evidence.
  • Co-Marketing Swap: Audience aligned, Campaign assets ready, Campaign launched, Results shared and Next steps agreed. Campaign launched and Results shared require evidence.
  • Mentorship: Goals defined, Session scheduled, Guidance delivered, Follow-up actions logged and Progress reflected on together. Guidance delivered requires evidence.

The mentorship reflection is a shared discussion about progress. It is separate from the private review submitted after completion. Rooms record the template version used for their engagement.

Milestones evidence and revisions

Each person confirms milestones independently. One confirmation produces a waiting state; the milestone is complete only when both participants confirm it. If a milestone requires evidence, the room must also contain the required evidence record.

Evidence can include a recorded link or explanation and supported file attachments. Shared files accept PDF, PNG, JPEG, WebP and UTF-8 text, with a 5 MB limit per file and a 50 MB upload allowance per account. Downloads require an authenticated session and appropriate room access. Uploads are not antivirus-scanned.

Changes to milestone scope use a revision proposal that the counterpart must review. Disputed work can be flagged for resolution. Open disputes and unresolved revision proposals prevent completion; checking a milestone is not a way to bypass these requirements.

Task board and chat

The board breaks work into cards with owners, priorities, milestone links and due dates. Move cards between To do, In progress and Done by dragging them or using the status menu. A completed card records task progress; it does not confirm a milestone for either participant.

Chat keeps the room's discussion with its agreement and work history. Participants can use it to clarify scope, arrange availability, share a meeting link and discuss evidence. Changes synchronize automatically with the other account through periodic API refreshes.

Mentorship scheduling and the calendar

The Schedule tab and the session milestone open the same planner. Select a date, time and duration, optionally create a weekly series, review it, and save. The planner does not check scheduling conflicts or connect to an external calendar or video service; participants agree on availability and a meeting link in Chat.

The workspace Calendar combines active-room sessions, open task deadlines and unconfirmed milestone deadlines. It supports Month and Agenda views, collaboration filtering and selected-day details. Sessions display in the viewer's device timezone. Task dates stay on their assigned date, while milestone deadlines retain their UTC date.

New schedules use the device timezone. Editing a saved series preserves its original timezone so a collaborator in another location does not accidentally shift the series.

Completing the engagement

Before Mark as launched or Complete mentorship can succeed, both people must agree to terms, both must confirm every milestone, required evidence must be present, and open disputes or revision proposals must be resolved. Mentorship must also have its session scheduled. The app reports blockers when these conditions are not satisfied.

7 Reviews trust and moderation

After completion, each participant submits a rating from one to five stars and can add written feedback. Optional questions ask whether the match was useful and whether the shared goal was achieved, partly achieved or not achieved.

The counterpart's feedback stays hidden until both reviews have been submitted. Once both are available, reviews are released and the collaboration enters Reviewed. This reduces the opportunity to tailor a rating in response to the other person's feedback, although it does not guarantee unbiased reviews.

Trust history includes completed engagements, released reviews, distinct reviewers, average rating, closed collaborations and follow-through. The aggregate average uses one rating per distinct partner account to limit repeated-partner inflation. An active engagement without an update for more than 14 days is counted as stalled. New accounts may have no rating or outcome history.

Users can report a collaborator from match details or a room. A report requires a reason and accepts optional details. It records authenticated reporter and reported-profile identifiers for the moderator queue. Reporting does not automatically block a person; blocking is a separate confirmed action.

Moderator privileges are limited to local password accounts listed in SYNERGY_ADMIN_EMAILS. Preview accounts do not receive them. Moderators can review reports and disputes, suspend accounts, review affiliation evidence and vocabulary proposals, manage reusable engagement templates and adjust matching weights. Decisions require a reason and are audited. Matching outcome summaries help moderators inspect results across algorithm versions and score ranges.

8 Settings and account controls

Settings includes Light and Dark appearance, active-profile switching, blocking and data export. Light is the first-visit default. An explicit appearance choice is saved in browser local storage and applied before the main interface renders.

The collapsed Danger zone contains visibility, session management and account deletion. These controls have different effects:

  • Pause visibility: removes the profile from discovery and pauses pending introductions while keeping existing rooms accessible.
  • Block a collaborator: withdraws introductions, closes unfinished rooms and prevents further chat between those participants.
  • Manage sessions: revokes selected sessions or other sessions through the account controls.
  • Export data: provides an account data export for the user.
  • Delete account: removes private account details, revokes sessions and anonymizes names in shared history. Agreements, evidence, messages and released reviews remain available to collaborators. Backup retention follows the operator's policy.

Voluntary sign-out requires confirmation. If the request fails, the current session and drafts remain available and the dialog supports retrying. A preview account has no user-facing password; deletion requires the current session and typing DELETE.

The API enforces account ownership and room membership. Profile photos are served only to the owner, eligible viewers or existing collaborators, and replaced photos are no longer served. These access checks do not imply end-to-end encryption.

9 Example journeys

A founder arranges a beta exchange

  1. A founder completes a profile explaining the product, what the team can offer and the testing help it needs.
  2. The founder checks Matches, opens a candidate's details and reviews both directions of need and offer coverage.
  3. The founder sends a Beta Testing Exchange introduction. The counterpart accepts and a room opens.
  4. Both agree on scope, testers, timing and the feedback deliverable in Terms.
  5. They create task cards, assign owners, set deadlines and discuss the testing process in Chat.
  6. They attach evidence for the testing round and submitted feedback, then independently confirm each milestone.
  7. After resolving any blockers, they mark the exchange as launched and submit their private reviews. Both reviews are released together.

A mentor guides a startup

  1. A mentor describes expertise, available support and the startups they want to help.
  2. The mentor reviews startup needs in Matches or responds to an incoming introduction.
  3. In the mentorship room, both agree on one clear challenge, a useful outcome, preparation and time commitment.
  4. They schedule a session or weekly series, then arrange the meeting link in Chat.
  5. The mentor records guidance evidence, both log follow-up actions, and they reflect on progress together.
  6. Both confirm every milestone, complete the mentorship, and submit separate private reviews.

These journeys require both participants' actions. For a demonstration of the full lifecycle, use two local accounts rather than relying on a fictional preview partner.

10 Technical structure and operations

Application architecture

The browser interface uses React 19, with Vite 8 for development and builds. Shared UI state, validation, routing and API synchronization live under src/state/. Domain rules and selectors live under src/data/, while screens and reusable controls are in src/pages/ and src/components/.

The Node.js backend provides the local JSON API, sessions, matching, account rules, rooms, files and moderation. Node.js 24 or later is required because storage uses its built-in SQLite module. The browser polls for shared updates approximately every 1.5 seconds; this is periodic synchronization rather than an external real-time messaging service.

Running the app

From the repository root, install dependencies and start the development server:

npm install
npm run dev

Vite normally serves the app at http://localhost:5173 and runs the API in the same process. For the built version:

npm run build
npm start

The built app normally uses http://localhost:4173. On Windows, use npm.cmd or npx.cmd when PowerShell script execution is restricted. The optional .env file controls demo mode, the data location, moderator emails, host, port and backup configuration.

Storage hosting and recovery

New workspaces use transactional SQLite with write-ahead logging at .data/synergy.sqlite. Uploads live beside the database in uploads/. Explicit JSON data paths remain supported. When an empty default database opens, a neighboring legacy synergy.json can be imported once while preserving the original.

Run a single application writer per database and use persistent storage for hosting. Serving only the frontend build directory cannot provide the API or preserve shared work. The repository includes a Render configuration for a Node service and persistent disk; hosting must be provisioned separately.

The health endpoint /api/health checks database integrity, a write probe and at least 20 MB of free disk. Its readiness result is cached for 30 seconds and it returns HTTP 503 when unavailable.

Use npm run backup -- /absolute/backup/directory to create a consistent snapshot outside the data directory. The backup records the database snapshot and referenced uploads with SHA-256 checksums. Verify it with node server/backup.js --verify /absolute/backup/snapshot. Copying an active SQLite database file by itself is insufficient because recent commits can remain in WAL journals.

Optional scheduled backups use SYNERGY_BACKUP_DIR and SYNERGY_BACKUP_INTERVAL_HOURS, which defaults to 24 hours. Failed scheduled backups retry after 15 minutes. The operator configures retention and off-site storage. Restore a verified database snapshot and its uploads together into a separate data directory, with the server stopped, then start one writer and check the restored records and downloads.

Verification tools

The repository includes Node unit and backend tests, Playwright browser tests, formatting checks, reference checks and a production build. The manual test runthrough covers role previews, local account workflows, moderation and account controls. Relevant commands are npm run test:unit, npm run test:e2e, npm run check:references, npm run check:format and npm run build. Browser tests require the Playwright browser installations.

11 Current scope and limitations

The current app provides local profile editing, explainable matching, introductions, shared rooms, terms, milestones, evidence, task boards, mentorship scheduling, calendar views, in-app updates, blind reviews and moderation.

The original product brief also describes ideas that are not active in this implementation. External email delivery, email verification, password recovery, email changes, email digests and AI profile drafting have been removed. Local tag suggestions use rules; the current matching engine is also rule-based. The Supabase migration document is a future plan, not the deployed storage architecture.

Scheduling does not connect to outside calendars or check conflicts. Synergy does not host video calls, and its terms do not implement payment processing. Participants arrange meeting access and any compensation separately. Fictional preview partners cannot provide the reciprocal actions required to finish a real engagement.

Changes are synchronized by polling, so the other tab may take a short time to update. Sessions end when the server restarts. Persistent storage, backups, retention and restore drills remain hosting responsibilities. These constraints matter when planning a demonstration or deciding what further work is needed for wider deployment.
